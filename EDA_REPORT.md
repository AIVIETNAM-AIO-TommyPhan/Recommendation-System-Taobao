## 1. Column roles — the generic inference is wrong here, by design

**Observation.** 16 of 19 modelling columns are integer-typed, so
`infer_column_kinds` calls them numeric and hands them to the numeric phase, which
computes skew, IQR fences and Pearson *r* on them. Two examples of what comes back:

**"`adgroup_id` skew −2.121, 6,728 IQR outliers, suggest log transform."** Every
statistic here is arithmetic on identifiers. Q1 = 619,783 and Q3 = 715,187, so the
IQR fence lands at [476,677, 858,293] and 6,728 impressions fall outside it. But the
"outliers" are just ads whose ID number happens to be small or large — ad `232014`
is not an anomalous ad, it is an ad with a low ID. Likewise the mean `adgroup_id`
is 660,710, a number with no referent, and the −2.121 skew describes how Taobao
allocated ID numbers, not anything about the ads. Log-transforming it would be
compressing the ID space.

**"`cms_segid` ~ `cms_group_id`, r = 0.984."** This one is subtler, because the
redundancy is *real* but the number is wrong twice over. The raw correlation across
all 240,000 rows is **0.453**, not 0.984 — the 0.984 only appears once the 55.6% of
rows with the `cms_segid = 0` sentinel are excluded, so the figure quoted in an
earlier draft silently conditioned on non-missing. And even 0.453 is meaningless as
a *linear* statistic: both columns are codes, so Pearson is measuring whether their
ID numbers were assigned in a compatible order. The genuine relationship is
functional, not linear — all **96** non-zero `cms_segid` levels map to exactly one
`cms_group_id`, i.e. `cms_segid` fully determines `cms_group_id`. That is a
user-side counterpart to the ad-side dependencies in §6, and correlation is the
wrong instrument to find it (see §6 for why).

![Column roles: ID magnitude vs CTR, and the segid→group step function](eda_out/report_figures/fig_column_roles.png)

The left panel plots every ad's CTR against its raw `adgroup_id` number. The grey
band is everything the IQR rule flags as an "outlier" (below fence 476,677 — no ad
reaches the upper fence 858,293). Those orange dots are not unusual ads: their CTR
(9%–31%) sits inside the same range as the blue dots that the rule left alone. The
rule is reacting only to the ID number being small, which carries no information —
compare that to `price` in §4, where the flagged tail (12,194 rows above ¥566.5) really
is the subset of genuinely expensive items.

The right panel plots every observed `(cms_segid, cms_group_id)` pair. If this were
a linear relationship the dots would scatter loosely around a rising line — instead
they form flat horizontal steps: every `cms_segid` on a step shares one, and only
one, `cms_group_id`. That step shape *is* the functional dependency, and it's why
correlation gives two different, both-wrong answers (0.453 / 0.984) depending on
which rows are included — Pearson *r* measures how well a straight line fits, and no
single line fits a staircase.

> **📘 Reading the numbers above, plainly.**
> - **Mean / Q1 / Q3** are just "average," "25th-percentile," and "75th-percentile"
>   value of the raw ID number. They're valid arithmetic, but since the ID number
>   itself is arbitrary (ad #85,419 isn't "less" of an ad than ad #842,734), the
>   arithmetic answers a question nobody's asking.
> - **Skew (−2.121)** measures whether a distribution leans left or right of its
>   mean (see §4 for the full mechanics). Applied to ID numbers it just describes
>   how Taobao happened to assign them — not a property of the ads.
> - **IQR outliers (6,728)** are points more than 1.5× the box-width beyond Q1/Q3
>   (the same fence rule used correctly for `price` in §4). Here the fence is drawn
>   on an arbitrary number line, so "outlier" only means "has a low or high ID," not
>   "behaves unusually" — the left panel is the proof.
> - **Correlation *r*** (−1 to 1) measures how well one column rises or falls in a
>   straight line with another. **0.453** (all rows) and **0.984** (55.6% of rows
>   with the sentinel dropped) are both real numbers, just answering the wrong
>   question — see the right panel: the true relationship is a 96-to-13 step
>   function, not a line, so no *r* value describes it well.

> **📘 The transferable rule.** An integer dtype does **not** mean the column is a
> quantity. If the numbers are *labels* (IDs, coded levels), their magnitude is
> arbitrary — mean, skew, IQR and Pearson *r* are all "arithmetic on ID numbers" and
> will mislead. Relationships among such columns are **functional** (does value A pin
> down value B?), found by a 1-to-1 mapping check, not **linear** (do they rise
> together?), found by correlation. Assign the role first; the statistic follows.

**Change.** `eda_scripts/prep_taobao.py` assigns real roles before analysis:

| Role | Columns |
|---|---|
| Continuous | `price` — **the only one** |
| Nominal ID | `adgroup_id`, `cate_id`, `campaign_id`, `customer`, `brand`, `cms_segid` |
| Ordinal code | `cms_group_id`, `age_level`, `pvalue_level`, `shopping_level`, `new_user_class_level` |
| Binary | `final_gender_code`, `occupation` |
| Cyclic | `hour`, `weekday` |
| Context | `pid` |
| Dropped | `userid` (147k values, row ID), `time_stamp` (superseded by `date`/`hour`/`weekday`) |

**Validate by:** the numeric phase reduces to `price` alone and the correlation
heatmap has nothing left to over-claim. Both hold in the re-run.

## 2. Target balance

`click` is 48,446 / 240,000 = **20.19%** positive (test 19.26%).

![Target balance and CTR](eda_out/report_figures/fig_target_balance.png)

The **imbalance ratio** is simply how many negatives there are per positive —
majority class ÷ minority class:

```
191,554 non-clicks / 48,446 clicks = 3.954
```

Equivalently `(1 − p) / p` with p = 0.201858. So there are ~4 non-clicks for every
click. A ratio of 1.0 is perfectly balanced; the common rule of thumb treats >10
as severe imbalance, so at 3.95 this dataset is **mildly** imbalanced — enough to
make accuracy useless, not enough to need resampling or class weights.

> **📘 Concept — why the ratio matters.** At 20% positives, a model that predicts
> "no click" for *everyone* already scores 80% accuracy while being useless — that is
> what "accuracy is uninformative under imbalance" means. Rank-and-probability metrics
> (**AUC**, **log loss**) don't have this blind spot because they score the predicted
> *probabilities*, not a single 0.5 threshold. At 3.95 the tilt is mild, so no
> resampling/class-weights are needed; those come into play nearer the >10 range.

Two things follow. First, accuracy at threshold 0.5 is uninformative — use AUC and
log loss, which the baseline already does. Second, **20% CTR is roughly 4× the ~5%
seen in real Taobao ad logs**, which is consistent with negatives having been
downsampled when the sample was built. This is a *hypothesis*: `Sample_Dataset.ipynb`
is not in the repo (it is in `.gitignore`), so it cannot be confirmed here.

If it is true, the practical consequence is that **predicted probabilities do not
transfer** — a model trained at 20% base rate will systematically over-predict
against a 5% production stream. Ranking metrics are unaffected; thresholds and
expected-value calculations are not. Recalibrate before any threshold is chosen.

Related: `Baseline_Model.ipynb` cell 4 says "CTR is heavily imbalanced (~5% positive)".
That comment is stale — the actual rate is 20%.

## 3. Missing values — all four are sentinels, none are informative

**Observation.** The files contain no `NaN`; missingness is encoded as `0`.
Decoding it is what makes this phase meaningful at all:

| Column | `0` share | Is `0` really missing? |
|---|---|---|
| `cms_segid` | 55.6% | yes — decoded |
| `pvalue_level` | 49.9% | yes — decoded (grades are 1–3) |
| `brand` | 48.0% | yes — decoded (131 of 300 ads have no brand) |
| `new_user_class_level` | 25.7% | yes — decoded (levels are 1–4) |
| `occupation` | 92.4% | **no** — 0 = "not a student", a real level |
| `final_gender_code` | — | **no** — coded 1/2, no 0 exists |
| `cms_group_id`, `age_level` | 0.03% | **no** — too rare for a sentinel; a small real bucket |

![0-sentinel share by column](eda_out/report_figures/fig_missing_sentinels.png)

**Is the missingness informative?** No — and this is the useful result:

| Column | CTR when missing | CTR when present |
|---|---|---|
| `brand` | 0.2015 | 0.2022 |
| `cms_segid` | 0.2015 | 0.2022 |
| `pvalue_level` | 0.2022 | 0.2015 |
| `new_user_class_level` | 0.2034 | 0.2013 |

Every gap is under 0.3pp against a 20.19% base rate. The methodology's threshold for
informative missingness is a 10pp spread across classes; nothing is close.

**Change.** Treat "unknown" as its own category and skip the `_is_missing`
indicators. For one-hot encoding this is free — "unknown" simply becomes another
level. The generic plan recommends an indicator for `cms_segid` purely because it
crosses 50%; that rule does not apply once we know the missingness carries no signal.
Do **not** median-impute these — the median of a set of brand IDs is meaningless.

**Validate by:** adding the indicators should leave held-out AUC unchanged. If it
moves, this conclusion is wrong.

> **📘 Concept — "unknown" category vs. missing-indicator.** These solve different
> jobs. Making "unknown" its own one-hot level (`pvalue_unknown`) lets the model
> *represent* the gap — that column already flags every missing row, for free. A
> separate `_is_missing` indicator is a *second* column that only pays off when the
> **act of being missing** itself predicts the target (e.g. users who hide income
> click far more). The table above shows the opposite: CTR differs by < 0.3pp between
> missing and present, so the indicator would just duplicate `*_unknown` with a
> near-zero coefficient. Keep the category, drop the indicator.

## 4. `price` — the only real numeric

Skew **1.964** (strongly right-skewed); `log1p` brings it to −0.530. 12,194 rows
(5.1%) are IQR outliers, all above ¥566.5 — genuine expensive items, not errors.

![price distribution and CTR by decile](eda_out/report_figures/fig_price.png)

The box plot makes the skew and the "outliers" concrete: the box (Q1 ¥99 – Q3 ¥286,
median ¥138) is squeezed to the left while a long tail of dots stretches to ¥999.
Everything past the upper fence (¥566.5) is flagged as an outlier — 12,194 points,
5.1% — but they are real expensive items, not errors. `log1p` (right) pulls the box
back to the centre and the tail almost vanishes.

| Box-plot marker | Value | Reading |
|---|---|---|
| min | ¥2.4 | cheapest item |
| Q1 (25th pct) | ¥99 | 25% of ads priced ≤ 99 |
| median (50th pct) | ¥138 | half priced ≤ 138 |
| Q3 (75th pct) | ¥286 | 75% priced ≤ 286 |
| max | ¥999 | dearest item |
| IQR = Q3 − Q1 | ¥187 | width of the box (middle 50%) |
| upper fence = Q3 + 1.5·IQR | ¥566.5 | anything past this is a plotted outlier |

![price box plot, raw vs log1p](eda_out/report_figures/fig_price_boxplot.png)

> **📘 Concept — Skewness (why 1.964).** Skew is a single unitless number for how
> *asymmetric* a distribution is: `skew = mean((x−x̄)³) / [mean((x−x̄)²)]^1.5`. The
> cube in the numerator **keeps the sign**, so a long right tail of dear items
> (¥999 → deviation³ ≈ +500M) outweighs the cheap side and the sum comes out
> **positive** → right-skew. Dividing by variance^1.5 cancels the ¥³ units, leaving
> 1.964. Rule of thumb: |skew| < 0.5 ≈ symmetric, > 1 = strongly skewed. Here
> mean ¥204.84 > median ¥138 is the same story in two numbers — the mean is dragged
> up by the tail, the median is not.

> **📘 Concept — why log1p flips the sign to −0.53.** `log1p(x) = log(1+x)` compresses
> large values far more than small ones (¥138→4.93, ¥999→6.91 — an 861-unit gap
> shrinks to ~2), so it pulls the right tail in and kills most of the skew. It
> slightly *over*-corrects at the low end (¥2.4 → 1.22 sits far left of the median
> 4.93), creating a faint **left** tail — that is why skew lands just past zero on the
> negative side. The sign only says which way it leans; |−0.53| ≪ |1.964|, so the
> shape is far more symmetric than before.

But the more important observation: **`price` has only 159 distinct values across
300 ads**, because it is an attribute of the ad, not of the impression. It is a
low-cardinality ad property wearing a continuous dtype.

And it barely moves the target. CTR by price decile stays in 0.174–0.229 with no
monotone trend — the cheapest decile (0.2222) and the most expensive (0.2051)
straddle the middle ones. Class-median separation is 0.0 std.

**Change.** `log1p` + `StandardScaler` for the linear baseline (cheap, fixes the
skew, no reason not to). Do not clip the tail. Expect little from it on its own —
its value is as an interaction with user features (price sensitivity by
`pvalue_level`), which a linear model cannot express without an explicit crossed term.

> **📘 Concept — StandardScaler.** It rescales a column to **mean 0, std 1** via the
> z-score `z = (x − mean) / std`. On `log1p(price)` (mean 5.03, std 0.77): ¥138 →
> z = −0.12 (right at the mean), ¥999 → z = +2.33 (2.3 std above), ¥2.4 → z = −4.73.
> Linear/distance models (logistic, SVM, kNN) are **scale-sensitive** — without this,
> a feature ranging 1–7 would dominate the 0/1 one-hot columns purely by magnitude and
> skew the gradient. Tree/GBM models don't need it (they compare thresholds, not
> weighted sums), which is why it's a *linear-baseline* step only. **Critical:** fit
> `mean`/`std` on **train only**, then apply to val/test — computing them over all rows
> leaks test information. That's why §Cleaning wraps `log1p → StandardScaler` in a
> `ColumnTransformer`.

## 5. Which features actually carry signal

Impression-weighted standard deviation of per-level CTR around the 20.19% base rate
— higher means the feature separates clicks better. Levels with <200 impressions
excluded so small-sample noise doesn't inflate the estimate.

| Feature | Levels | CTR range | Weighted SD |
|---|---|---|---|
| `adgroup_id` | 297 | 0.077 – 0.452 | **0.0532** |
| `campaign_id` | 248 | 0.077 – 0.452 | 0.0505 |
| `customer` | 213 | 0.077 – 0.452 | 0.0484 |
| `brand` | 116 | 0.115 – 0.362 | 0.0334 |
| `cate_id` | 44 | 0.129 – 0.356 | 0.0238 |
| `cms_group_id` | 12 | 0.185 – 0.239 | 0.0113 |
| `age_level` | 6 | 0.188 – 0.226 | 0.0108 |
| `cms_segid` | 52 | 0.158 – 0.250 | 0.0096 |
| `pid` | 2 | 0.195 – 0.213 | 0.0086 |
| `hour` | 24 | 0.185 – 0.223 | 0.0060 |
| `occupation` | 2 | 0.200 – 0.219 | 0.0049 |
| `weekday` | 7 | 0.195 – 0.211 | 0.0048 |
| `new_user_class_level` | 5 | 0.196 – 0.206 | 0.0037 |
| `pvalue_level` | 4 | 0.185 – 0.204 | 0.0030 |
| `final_gender_code` | 2 | 0.195 – 0.203 | 0.0027 |
| `shopping_level` | 3 | 0.201 – 0.203 | **0.0004** |

![Feature signal strength](eda_out/report_figures/fig_feature_signal.png)

> **📘 Concept — Weighted SD (how the ranking is computed).** For each feature it asks
> one question: *do its levels have genuinely different CTRs?* Formula:
> `WSD = sqrt( Σ_level  w_i · (CTR_i − 0.2019)² )`, where `w_i` is that level's share of
> impressions. Read it in four steps — (1) how far each level's CTR sits from the
> 20.19% base, (2) **square** it (drops the sign, punishes big gaps — same idea as
> variance), (3) **weight by impressions** so a rare level with a freak CTR can't
> dominate, (4) **square-root** back into CTR units so it's readable. Worked example,
> `pid` (2 levels): 0.2125 at weight 0.39 and 0.1949 at weight 0.61 →
> `sqrt(0.000045 + 0.000029) = 0.0086`. The impression-weighting — plus dropping levels
> under 200 impressions — is what makes this a *real-signal* estimate, not small-sample
> noise: an ad seen 10 times at 60% CTR does **not** inflate the score.

**The ad identity carries an order of magnitude more signal than any user
attribute.** `adgroup_id` alone spans 7.7%–45.2% CTR. Every user demographic sits
under 0.012 — `shopping_level` is essentially constant (0.201/0.202/0.203) and is
the weakest feature in the dataset.

This is expected for CTR: *which ad* dominates *who saw it*, and user features earn
their keep through interactions (this user × this category), not as main effects.
A linear model with only main effects will capture almost none of that — the single
biggest modelling gain available here is crossed features or a tree/FM model.

**Change.** Keep the weak user features (they matter in interactions) but do not
expect main-effect lift. Prioritise `adgroup_id`/`cate_id` × user-segment crosses.
**Validate by:** whether adding crosses beats the main-effects-only baseline AUC.

## 6. Redundancy is functional, not linear

> **📘 In plain terms — the ZIP-code analogy.** "Functional dependence" just means
> *one column decides another*. Think of a postal ZIP code: once you know it, the city
> and state are already fixed — storing them in separate columns adds nothing new.
> Here **`adgroup_id` is the ZIP code**: knowing *which ad* it is automatically fixes
> its category, brand, price, campaign, and advertiser. So those five columns aren't
> five independent clues — they're one ad's attributes written five times. Two
> consequences: (1) feeding all of them to a linear model is repetition, not extra
> signal; (2) correlation can't detect this, because correlation only measures
> *numbers moving up and down together*, and these are **labels, not quantities**
> (§1). You find it instead by asking "does each value of A map to exactly one value
> of B?" — and here the answer is yes, with no exceptions.

The correlation heatmap now finds no strong pairs — correct, since Pearson on
`price` alone has nothing to compare. But real redundancy exists and is invisible to
correlation, because it is functional dependence among categoricals:

```
ad side:    adgroup_id ─→ cate_id, brand, price   (all 300 map 1:1 — no exceptions)
            adgroup_id ─→ campaign_id ─→ customer  (each 1:1)
user side:  cms_segid  ─→ cms_group_id             (all 96 non-zero levels 1:1)
```

`adgroup_id` **determines** the other five. Given `adgroup_id`, they add zero
information; the CTR-spread table above shows exactly this (0.0532 / 0.0505 / 0.0484
for `adgroup_id` / `campaign_id` / `customer` — the same signal, progressively
coarsened).

The user-side pair works the same way: each of the 96 real `cms_segid` micro-groups
sits inside exactly one of the 13 `cms_group_id` buckets, so `cms_group_id` is a
coarsening of `cms_segid` and adds nothing once the finer column is encoded. The one
caveat is the sentinel — 55.6% of rows have `cms_segid = 0` (unknown) but still carry
a real `cms_group_id`, so the coarse column is the *only* user-segment signal
available on the majority of rows. Keep both: `cms_group_id` is the backoff for
exactly the rows where `cms_segid` is missing.

Worse, `campaign_id` is near-useless here: the top-300 filter left 248 campaigns for
300 ads, and **217 campaigns contain exactly one ad**. One-hot encoding both is close
to encoding the same column twice.

**Change.** For a linear model, encode `adgroup_id` and keep `cate_id`/`brand` only
as backoff for low-traffic ads; drop `campaign_id` and `customer`. Note the baseline
notebook excludes them for a reason that is now stale — it says they are "near-unique
IDs (tens of thousands of categories)", but after the top-300 filter they are 248 and
213. The right reason is redundancy, not cardinality.

## 7. Encoding

The generic plan says target/frequency-encode everything above 20 levels. Two
overrides:

- **`hour` (24 levels) → not high-cardinality.** One-hot it, or better, encode
  cyclically (`sin`/`cos` of `2πh/24`) so hour 23 sits next to hour 0. Target-encoding
  a cyclic feature discards the ordering for no benefit.
- **`adgroup_id` (300 levels) → one-hot is fine and is what the baseline does.** The
  top-300 filter was applied precisely so this would work: every ad has ~800
  impressions on average, enough to learn its own coefficient. Target-encoding it
  would need out-of-fold fitting to avoid leakage — more machinery, no clear gain at
  this cardinality.

Genuine target/frequency-encoding candidates: none, once `campaign_id` and
`customer` are dropped as redundant.

The "rare categories" counts in the generated table (e.g. "`adgroup_id`: 293 rare")
are an artefact of a <1%-share threshold — with 300 roughly balanced levels, almost
every level is under 1%. These are not rare categories and should not be grouped
into "Other".

## 8. Train/test consistency

**No unseen levels.** All of `adgroup_id`, `cate_id`, `campaign_id`, `customer`,
`brand`, `pid`, `cms_segid` appear in test with **zero** unseen levels — guaranteed
by the fixed 300-ad catalog. (Test exercises 286 of the 300 ads; the other 14 simply
drew no impressions in the 1.5-day window.)

**But the ad mix does shift, and the generic phase misses it.** The phase only
computes PSI on numerics, so it sees `price` PSI 0.0486 and reports "small". The
shift lives in the categoricals. Total variation distance, train vs test:

| Feature | TVD | |
|---|---|---|
| `adgroup_id` | **0.277** | large |
| `cate_id` | 0.087 | moderate |
| `age_level` | 0.031 | negligible |
| `pid` | 0.024 | negligible |
| `final_gender_code` | 0.006 | negligible |

![Train/test distribution shift](eda_out/report_figures/fig_train_test_shift.png)

Which ads get served changes materially between the two windows — the most-served
train ad (`710164`, 4.0% of impressions) drops to 2.0% in test, while `836889` rises
to 3.9%. `price` follows it: train mean ¥204.84 / median ¥138 vs test mean ¥230.71 /
median ¥162. Since §5 shows `adgroup_id` is by far the strongest feature, a shift in
*which* ads dominate is exactly the shift that matters most here.

**Consequence.** Expect the test score to sit below validation even with a correct
temporal split, and read a gap as mix shift before assuming overfitting. The user
side is stable, so this is an ad-serving change, not a population change.
**Validate by:** scoring per-`adgroup_id` and confirming the loss concentrates in
ads whose impression share moved, not uniformly.

Two more issues:

**`date` cannot be used as a feature.** Train covers 05-05…05-12, test covers
05-12…05-13. `2017-05-13` never appears in train, so its one-hot column is always
zero at fit time and the model has no coefficient for the majority of test days.
Drop `date`; `hour` and `weekday` carry the usable time signal. (The baseline
already does this.) Note that `date` is the *only* column the train/test phase flags
with an unseen level — every ad-side and user-side category is fully covered.

**Validation splits must be temporal, not random.** The test set is a strict future
holdout (every test impression post-dates every train impression), so a random
`KFold` on train would let the model see future impressions of the same ad and
report an optimistic score. Use `TimeSeriesSplit` or a fixed cutoff — e.g. hold out
05-11…05-12 — so validation mirrors the real split.

Note that 20,508 of 47,608 test users also appear in train. That is not leakage —
it's the same users returning on a later day, which is exactly the production
setting.

## Cleaning & transformation plan

Fit on train only, then apply to validation/test.

1. **Load with a timestamp guard** (§0) — the Excel-mangling failure is silent.
2. **Drop** `userid`, `time_stamp`, `date` (§1, §8); **drop** `campaign_id`,
   `customer` as functionally redundant with `adgroup_id` (§6).
3. **Decode `0` → "unknown"** in `brand`, `cms_segid`, `pvalue_level`,
   `new_user_class_level`, and keep it as a category. No imputation, no missing
   indicators (§3).
4. **`price`**: `log1p`, then `StandardScaler` (§4).
5. **One-hot**: `adgroup_id`, `cate_id`, `brand`, `pid`, `cms_segid`, `cms_group_id`,
   `final_gender_code`, `age_level`, `pvalue_level`, `shopping_level`, `occupation`,
   `new_user_class_level`, `weekday`, with `handle_unknown="ignore"` (§7).
6. **`hour`**: cyclic `sin`/`cos` encoding (§7).
7. **Validation**: temporal split, not random `KFold` (§8).
8. **Then** add `adgroup_id`/`cate_id` × user-segment crosses, or move to a
   tree/FM model — §5 says this is where the headroom is, not in more preprocessing.

Build steps 3–6 as an sklearn `ColumnTransformer` so they stay leak-free and
reproducible; `eda_scripts/transform.py` has a configurable implementation.
