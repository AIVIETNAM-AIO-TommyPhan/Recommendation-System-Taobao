# EDA Report — Taobao CTR dataset

`dataset/train.csv` (240,000 × 21) and `dataset/test.csv` (60,000 × 21), target `click`.

Generated by `eda_scripts/eda_taobao.py`; the auto-generated draft is in
`eda_out/report_generated.md`, plots in `eda_out/plots/`. This file is the reviewed version — it
corrects two places where the generic heuristics give the wrong advice for this
dataset, and adds findings the generic phases cannot see.

reloaded and the damage is gone:

Both files now parse with a single `format=`, and the README's `04:24:15` split

df["time_stamp"] = pd.to_datetime(df["time_stamp"])

**On duplicates.** 11,786 rows share a `(userid, time_stamp)` key but **zero** are

## 1. Column roles — the generic inference is wrong here, by design

**Observation.** 16 of 19 modelling columns are integer-typed, so
`infer_column_kinds` calls them numeric. Running the phases that way produced
"`adgroup_id` skew −2.121, 6,728 IQR outliers, suggest log transform" and
"`cms_segid` ~ `cms_group_id`, r = 0.984" — arithmetic on identifiers, meaningless.

**Change.** `eda_scripts/prep_taobao.py` assigns real roles before analysis:

| Role | Columns |
|---|---|
| Continuous | `price` — **the only one** |
| Nominal ID | `adgroup_id`, `cate_id`, `campaign_id`, `customer`, `brand`, `cms_segid` |
| Ordinal code | `cms_group_id`, `age_level`, `pvalue_level`, `shopping_level`, `new_user_class_level` |
| Binary | `final_gender_code`, `occupation` |
| Cyclic | `hour`, `weekday` |
| Context | `pid` |
| Dropped | `userid` (147k values, row ID), `time_stamp` (superseded by `date`/`hour`/`weekday`) |

**Validate by:** the numeric phase reduces to `price` alone and the correlation
heatmap has nothing left to over-claim. Both hold in the re-run.

## 2. Target balance

`click` is 48,446 / 240,000 = **20.19%** positive (test 19.26%), imbalance ratio 3.95.

Two things follow. First, accuracy at threshold 0.5 is uninformative — use AUC and
log loss, which the baseline already does. Second, **20% CTR is roughly 4× the ~5%
seen in real Taobao ad logs**, which is consistent with negatives having been
downsampled when the sample was built. This is a *hypothesis*: `Sample_Dataset.ipynb`
is not in the repo (it is in `.gitignore`), so it cannot be confirmed here.

If it is true, the practical consequence is that **predicted probabilities do not
transfer** — a model trained at 20% base rate will systematically over-predict
against a 5% production stream. Ranking metrics are unaffected; thresholds and
expected-value calculations are not. Recalibrate before any threshold is chosen.

Related: `Baseline_Model.ipynb` cell 4 says "CTR is heavily imbalanced (~5% positive)".
That comment is stale — the actual rate is 20%.

## 3. Missing values — all four are sentinels, none are informative

**Observation.** The files contain no `NaN`; missingness is encoded as `0`.
Decoding it is what makes this phase meaningful at all:

| Column | `0` share | Is `0` really missing? |
|---|---|---|
| `cms_segid` | 55.6% | yes — decoded |
| `pvalue_level` | 49.9% | yes — decoded (grades are 1–3) |
| `brand` | 48.0% | yes — decoded (131 of 300 ads have no brand) |
| `new_user_class_level` | 25.7% | yes — decoded (levels are 1–4) |
| `occupation` | 92.4% | **no** — 0 = "not a student", a real level |
| `final_gender_code` | — | **no** — coded 1/2, no 0 exists |
| `cms_group_id`, `age_level` | 0.03% | **no** — too rare for a sentinel; a small real bucket |

**Is the missingness informative?** No — and this is the useful result:

| Column | CTR when missing | CTR when present |
|---|---|---|
| `brand` | 0.2015 | 0.2022 |
| `cms_segid` | 0.2015 | 0.2022 |
| `pvalue_level` | 0.2022 | 0.2015 |
| `new_user_class_level` | 0.2034 | 0.2013 |

Every gap is under 0.3pp against a 20.19% base rate. The methodology's threshold for
informative missingness is a 10pp spread across classes; nothing is close.

**Change.** Treat "unknown" as its own category and skip the `_is_missing`
indicators. For one-hot encoding this is free — "unknown" simply becomes another
level. The generic plan recommends an indicator for `cms_segid` purely because it
crosses 50%; that rule does not apply once we know the missingness carries no signal.
Do **not** median-impute these — the median of a set of brand IDs is meaningless.

**Validate by:** adding the indicators should leave held-out AUC unchanged. If it
moves, this conclusion is wrong.

## 4. `price` — the only real numeric

Skew **1.964** (strongly right-skewed); `log1p` brings it to −0.530. 12,194 rows
(5.1%) are IQR outliers, all above ¥566.5 — genuine expensive items, not errors.

But the more important observation: **`price` has only 159 distinct values across
300 ads**, because it is an attribute of the ad, not of the impression. It is a
low-cardinality ad property wearing a continuous dtype.

And it barely moves the target. CTR by price decile stays in 0.174–0.229 with no
monotone trend — the cheapest decile (0.2222) and the most expensive (0.2051)
straddle the middle ones. Class-median separation is 0.0 std.

**Change.** `log1p` + `StandardScaler` for the linear baseline (cheap, fixes the
skew, no reason not to). Do not clip the tail. Expect little from it on its own —
its value is as an interaction with user features (price sensitivity by
`pvalue_level`), which a linear model cannot express without an explicit crossed term.

## 5. Which features actually carry signal

Impression-weighted standard deviation of per-level CTR around the 20.19% base rate
— higher means the feature separates clicks better. Levels with <200 impressions
excluded so small-sample noise doesn't inflate the estimate.

| Feature | Levels | CTR range | Weighted SD |
|---|---|---|---|
| `adgroup_id` | 297 | 0.077 – 0.452 | **0.0532** |
| `campaign_id` | 248 | 0.077 – 0.452 | 0.0505 |
| `customer` | 213 | 0.077 – 0.452 | 0.0484 |
| `brand` | 116 | 0.115 – 0.362 | 0.0334 |
| `cate_id` | 44 | 0.129 – 0.356 | 0.0238 |
| `cms_group_id` | 12 | 0.185 – 0.239 | 0.0113 |
| `age_level` | 6 | 0.188 – 0.226 | 0.0108 |
| `cms_segid` | 52 | 0.158 – 0.250 | 0.0096 |
| `pid` | 2 | 0.195 – 0.213 | 0.0086 |
| `hour` | 24 | 0.185 – 0.223 | 0.0060 |
| `occupation` | 2 | 0.200 – 0.219 | 0.0049 |
| `weekday` | 7 | 0.195 – 0.211 | 0.0048 |
| `new_user_class_level` | 5 | 0.196 – 0.206 | 0.0037 |
| `pvalue_level` | 4 | 0.185 – 0.204 | 0.0030 |
| `final_gender_code` | 2 | 0.195 – 0.203 | 0.0027 |
| `shopping_level` | 3 | 0.201 – 0.203 | **0.0004** |

**The ad identity carries an order of magnitude more signal than any user
attribute.** `adgroup_id` alone spans 7.7%–45.2% CTR. Every user demographic sits
under 0.012 — `shopping_level` is essentially constant (0.201/0.202/0.203) and is
the weakest feature in the dataset.

This is expected for CTR: *which ad* dominates *who saw it*, and user features earn
their keep through interactions (this user × this category), not as main effects.
A linear model with only main effects will capture almost none of that — the single
biggest modelling gain available here is crossed features or a tree/FM model.

**Change.** Keep the weak user features (they matter in interactions) but do not
expect main-effect lift. Prioritise `adgroup_id`/`cate_id` × user-segment crosses.
**Validate by:** whether adding crosses beats the main-effects-only baseline AUC.

## 6. Redundancy is functional, not linear

The correlation heatmap now finds no strong pairs — correct, since Pearson on
`price` alone has nothing to compare. But real redundancy exists and is invisible to
correlation, because it is functional dependence among categoricals:

```
adgroup_id ─→ cate_id, brand, price   (all 300 map 1:1 — verified, no exceptions)
adgroup_id ─→ campaign_id ─→ customer  (each 1:1)
```

`adgroup_id` **determines** the other five. Given `adgroup_id`, they add zero
information; the CTR-spread table above shows exactly this (0.0532 / 0.0505 / 0.0484
for `adgroup_id` / `campaign_id` / `customer` — the same signal, progressively
coarsened).

Worse, `campaign_id` is near-useless here: the top-300 filter left 248 campaigns for
300 ads, and **217 campaigns contain exactly one ad**. One-hot encoding both is close
to encoding the same column twice.

**Change.** For a linear model, encode `adgroup_id` and keep `cate_id`/`brand` only
as backoff for low-traffic ads; drop `campaign_id` and `customer`. Note the baseline
notebook excludes them for a reason that is now stale — it says they are "near-unique
IDs (tens of thousands of categories)", but after the top-300 filter they are 248 and
213. The right reason is redundancy, not cardinality.

## 7. Encoding

The generic plan says target/frequency-encode everything above 20 levels. Two
overrides:

- **`hour` (24 levels) → not high-cardinality.** One-hot it, or better, encode
  cyclically (`sin`/`cos` of `2πh/24`) so hour 23 sits next to hour 0. Target-encoding
  a cyclic feature discards the ordering for no benefit.
- **`adgroup_id` (300 levels) → one-hot is fine and is what the baseline does.** The
  top-300 filter was applied precisely so this would work: every ad has ~800
  impressions on average, enough to learn its own coefficient. Target-encoding it
  would need out-of-fold fitting to avoid leakage — more machinery, no clear gain at
  this cardinality.

Genuine target/frequency-encoding candidates: none, once `campaign_id` and
`customer` are dropped as redundant.

The "rare categories" counts in the generated table (e.g. "`adgroup_id`: 293 rare")
are an artefact of a <1%-share threshold — with 300 roughly balanced levels, almost
every level is under 1%. These are not rare categories and should not be grouped
into "Other".

## 8. Train/test consistency

**No unseen levels.** All of `adgroup_id`, `cate_id`, `campaign_id`, `customer`,
`brand`, `pid`, `cms_segid` appear in test with **zero** unseen levels — guaranteed
by the fixed 300-ad catalog. (Test exercises 286 of the 300 ads; the other 14 simply
drew no impressions in the 1.5-day window.)

**But the ad mix does shift, and the generic phase misses it.** The phase only
computes PSI on numerics, so it sees `price` PSI 0.0486 and reports "small". The
shift lives in the categoricals. Total variation distance, train vs test:

| Feature | TVD | |
|---|---|---|
| `adgroup_id` | **0.277** | large |
| `cate_id` | 0.087 | moderate |
| `age_level` | 0.031 | negligible |
| `pid` | 0.024 | negligible |
| `final_gender_code` | 0.006 | negligible |

Which ads get served changes materially between the two windows — the most-served
train ad (`710164`, 4.0% of impressions) drops to 2.0% in test, while `836889` rises
to 3.9%. `price` follows it: train mean ¥204.84 / median ¥138 vs test mean ¥230.71 /
median ¥162. Since §5 shows `adgroup_id` is by far the strongest feature, a shift in
*which* ads dominate is exactly the shift that matters most here.

**Consequence.** Expect the test score to sit below validation even with a correct
temporal split, and read a gap as mix shift before assuming overfitting. The user
side is stable, so this is an ad-serving change, not a population change.
**Validate by:** scoring per-`adgroup_id` and confirming the loss concentrates in
ads whose impression share moved, not uniformly.

Two more issues:

**`date` cannot be used as a feature.** Train covers 05-05…05-12, test covers
05-12…05-13. `2017-05-13` never appears in train, so its one-hot column is always
zero at fit time and the model has no coefficient for the majority of test days.
Drop `date`; `hour` and `weekday` carry the usable time signal. (The baseline
already does this.) Note that `date` is the *only* column the train/test phase flags
with an unseen level — every ad-side and user-side category is fully covered.

**Validation splits must be temporal, not random.** The test set is a strict future
holdout (every test impression post-dates every train impression), so a random
`KFold` on train would let the model see future impressions of the same ad and
report an optimistic score. Use `TimeSeriesSplit` or a fixed cutoff — e.g. hold out
05-11…05-12 — so validation mirrors the real split.

Note that 20,508 of 47,608 test users also appear in train. That is not leakage —
it's the same users returning on a later day, which is exactly the production
setting.

## Cleaning & transformation plan

Fit on train only, then apply to validation/test.

1. **Load with a timestamp guard** (§0) — the Excel-mangling failure is silent.
2. **Drop** `userid`, `time_stamp`, `date` (§1, §8); **drop** `campaign_id`,
   `customer` as functionally redundant with `adgroup_id` (§6).
3. **Decode `0` → "unknown"** in `brand`, `cms_segid`, `pvalue_level`,
   `new_user_class_level`, and keep it as a category. No imputation, no missing
   indicators (§3).
4. **`price`**: `log1p`, then `StandardScaler` (§4).
5. **One-hot**: `adgroup_id`, `cate_id`, `brand`, `pid`, `cms_segid`, `cms_group_id`,
   `final_gender_code`, `age_level`, `pvalue_level`, `shopping_level`, `occupation`,
   `new_user_class_level`, `weekday`, with `handle_unknown="ignore"` (§7).
6. **`hour`**: cyclic `sin`/`cos` encoding (§7).
7. **Validation**: temporal split, not random `KFold` (§8).
8. **Then** add `adgroup_id`/`cate_id` × user-segment crosses, or move to a
   tree/FM model — §5 says this is where the headroom is, not in more preprocessing.

Build steps 3–6 as an sklearn `ColumnTransformer` so they stay leak-free and
reproducible; `eda_scripts/transform.py` has a configurable implementation.
